## BUG 1 + BUG 3 — Meal display shows name only, no ingredients or grams

### Symptom
- Dashboard meal cards show no gram amounts or ingredient list.
- Food log section shows "My protein lunch" or "Food log" as the label — not ingredient names and gram amounts.

### Root cause
FoodLogItem renders log.custom_food_name or meal_type as the label. When a log has a meal_id, the component never fetches the meal detail to expand ingredients. The API endpoint GET /api/v1/meals/{meal_id} returns a full ingredients array — it is just never called.

### Fix required
1. In the component that renders each food log entry (FoodLogItem or equivalent):
   - If the log has a meal_id, fetch GET /api/v1/meals/{meal_id} on mount.
   - Render the meal name as the primary label.
   - Below the name, render each ingredient as: "{ingredient_name}  {grams}g"
   - Example: "Salmon 150g · Quinoa 80g · Spinach 60g"
2. In DashboardPage, apply the same ingredient expansion to any meal card shown in today's meal summary.
3. If the log has custom_food_name and no meal_id, display the custom name as-is — no fetch needed.
4. Do not show "Food log" or raw meal_type as the visible label anywhere.

### Verify
After fix: logging a curated meal shows its name + each ingredient with grams in both the meal log page and the dashboard.

## BUG 2 — Saved meal list stays visible after logging

### Symptom
After user selects and logs a meal from the saved/recent meals list, the list remains on screen. User sees a stack of previously saved meals even after successfully logging one, which is confusing.

### Root cause
After POST /food-logs succeeds, React Query invalidates ["food-logs","today"] but the local UI state controlling the saved meals list (selected food state, recent meals display) is not reset. The list is driven by local state, not the cache.

### Fix required
In MealLogPage.jsx, after a successful meal log submission:
1. Clear selected food state (setSelectedFood(null) or equivalent).
2. Collapse or hide the recent/saved meals list — set its visibility state to false.
3. Show a brief inline success confirmation ("Meal logged") where the list was, then let the user initiate a new log if they want.
4. Do NOT clear the list on page mount — only on successful submission.

### Verify
After fix: log a meal → saved meals list disappears → success message shown → user can tap to add another meal.

## BUG 4 — Acceptance rate shows two different numbers (4% vs 29%)

### Symptom
The "Accepted" metric card in the Insights/Analytics screen shows ~4%.
The weekly adherence bar or insights text shows ~29%.
Both claim to represent recommendation acceptance but use different calculations.

### Root cause
Two different formulas are in use:
- Card: accepted_count / total_recommendations_shown (includes recommendations never interacted with)
- Bar: accepted_count / (accepted_count + skipped_count) (only counts interactions)

These measure different things and are both unlabelled, causing confusion.

### Fix required
Backend — app/services/dashboard_service.py:
1. Define ONE acceptance rate: accepted_count / (accepted_count + skipped_count). Only include recommendation_logs where feedback_status is not null.
2. Return this as recommendation_acceptance_rate in GET /api/v1/dashboard/weekly.
3. Remove or stop returning any secondary acceptance calculation.

Frontend — AnalyticsPage.jsx:
1. Read only recommendation_acceptance_rate from the weekly response.
2. Remove the duplicate metric source.
3. Both the card and the bar must read from this single field.
4. Label the card clearly: "Accepted (of decisions made)" so the denominator is transparent.

### Verify
After fix: both the card and the bar show the same number. The label clarifies what is being measured.
